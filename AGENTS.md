# Development rules

- Build one small working part at a time.
- Keep a working version before adding a new feature.
- Test each part before combining parts.
- Keep code simple enough for me to understand and explain.
- Follow strong Python practice.
- Follow PEP 8 for Python.
- Use clear names, type hints and concise docstrings where useful.
- Add input validation and safe error handling where useful.
- Do not overengineer small tasks.
- Explain every new package before installing it.
- Follow UI/UX, Universal Design and usability best practice.
- Design for accessibility and low cognitive load.
- Use clear information hierarchy, readable text, sufficient contrast,
  large usable controls, keyboard access where relevant, responsive layouts,
  consistent patterns and clear feedback and error states.
- Keep live presentation cues short, discreet and readable at a glance.
- Do not add features merely because they are possible.
- A small finished build is better than a large unfinished build.
- Never claim to know a person's true emotion from facial or voice signals.
- Treat camera and audio measures as observable cues.
- Audience Pulse estimates group engagement trends, not emotion.
- Do not identify audience members.
- Do not store facial images unless there is a clear reason and permission.
- Review existing code before changing it.
- Test changes rather than assuming they work.
